# Unity texture-paint backend: verified API facts and proposed architecture

Research date: 2026-10-02. This is a design recommendation, not an implementation or benchmark report. No Unity project was run and no performance, device compatibility, or image-fidelity result has been measured. API existence is distinguished below from architectural inference. The user's Unity version, render pipeline, operating systems and tablet models remain unconfirmed.

## 1. Recommended architecture and compatibility contract

**Proposed decision:** a dedicated `EditorWindow` with a retained UI Toolkit shell, independent paint document model, renderer-only preview scene, tiled GPU paint/compositor backend, plain-data Burst/Jobs geometry workers, and a versioned disk-backed document/undo store. Isolate input, rendering, serialization and material mapping behind adapters. Retain an IMGUI viewport/input adapter where the selected Unity version or a validated pen driver benefits from it; do not duplicate incoming pointer and synthetic mouse strokes.

**Version gate:** use 2022.3 documentation as evidence that the core design does not require Unity 6. This is not a commitment to support every 2022.3 patch or an assertion that 2022.3 is the user's version or the appropriate current release. Confirm the exact supported Editor versions, OS, graphics API, Built-in/URP/HDRP and lilToon versions first. Pin matching Burst, Collections and optional Input System packages, compile/test each supported combination, and hide unsupported paths behind explicit capabilities. Avoid an unconditional dependency on newer Awaitable/RenderGraph APIs. A compatibility floor and support lifecycle require a separate product decision.

Relevant primary sources:
- [Unity 2022.3 custom Editor window and CreateGUI](https://docs.unity3d.com/2022.3/Documentation/Manual/UIE-HowTo-CreateEditorWindow.html)
- [Unity 2022.3 IMGUI/UI Toolkit migration and IMGUIContainer](https://docs.unity3d.com/2022.3/Documentation/Manual/UIE-IMGUI-migration.html)
- [Burst 1.8 supported C#/.NET types](https://docs.unity3d.com/Packages/com.unity.burst@1.8/manual/csharp-type-support.html)

## 2. Window, input and pressure

**Verified:** UI Toolkit provides pointer-device information including pressure and tilt; pointer events precede mouse events. The 2022.3 IMGUI `Event.pressure` API normalizes pressure to 0–1 and reports 1 for unsupported devices. `ListView` pools/reuses visible rows. UI Toolkit's `CreateGUI` is the proper point for constructing controls and registering callbacks. These facts do not establish pen latency, sample frequency or reliable pressure on every driver.

**Proposed:** use virtualized layer/asset lists, reusable controls and a RenderTexture displayed in a dedicated canvas element. One input adapter owns a captured stroke from down to up/cancel/lost focus. Normalize timestamps, pointer ID, position, buttons, pressure, tilt and twist into immutable samples. Apply a user-editable pressure curve, fixed-pressure mouse fallback, and independent mappings to radius/opacity/flow. Resample by distance rather than repaint frequency; retain samples when display frames are skipped. End or cancel strokes deterministically on focus loss, reload, capture loss and window closure. High-DPI coordinates, tablet-to-monitor mapping, hover, eraser, pen buttons and input outside the canvas need device tests. Do not force project-wide Input System settings solely for this editor tool.

UI Toolkit versus IMGUI is a maintenance/input compatibility choice; neither has been benchmarked as inherently faster for this application. A hybrid shell with an IMGUI viewport is a contingency, not a second required full UI implementation. Input System pen support is a separate package-level capability and does not by itself prove EditorWindow behavior or Windows driver support.

Sources: [pointer events, 2022.3](https://docs.unity3d.com/2022.3/Documentation/Manual/UIE-Pointer-Events.html); [Event.pressure, 2022.3](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Event-pressure.html); [Input System 1.7 pen support and limitations](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.7/manual/Pen.html)

## 3. Preview isolation: what can and cannot be guaranteed

**Verified:** `EditorSceneManager.NewPreviewScene` restricts objects in that scene to rendering there. RenderTextures can serve as a camera target. Unity's own `PreviewRenderUtility` source uses a preview scene and explicitly requires `Cleanup`; its current source must not be treated as proof of identical behavior in old versions. `ExecuteAlways` scripts can run during editing.

**Proposed:** create only a renderer/bone/transform representation in the preview scene, with owned cloned materials and tool-owned camera/lights/RenderTextures. Read source meshes and source textures without modifying them. Do not blindly instantiate arbitrary user prefabs then try to disable scripts afterward: editor-executing components can already have run. Prefer extracting the supported render components into controlled objects. Keep material binding and mesh sampling separate from source scene ownership; explicit Apply/Export is the boundary for asset changes. Use preview-owned collider/BVH data, never global scene raycasts for picking. Avoid editing `Selection`, active scene, source renderer material arrays, global shader keywords, project settings or camera stacks as part of a stroke.

Choose between `PreviewRenderUtility` and a manually owned `NewPreviewScene` + camera + RenderTexture behind a version/pipeline adapter after a small compatibility spike. Guarantee cleanup, restore any unavoidable temporary render state with `try/finally`, and separate tool-neutral material preview from exact target-shader preview. Exact SRP/custom-shader parity is a tested adapter feature, not an automatic consequence of preview-scene isolation.

**Honest isolation limit:** this remains inside the same Unity Editor process and graphics device. Other extensions, render callbacks, shader globals, project imports, GC, compilation, job workers and GPU/VRAM compete. A preview scene does not sandbox arbitrary scripts, prevent driver resets, or guarantee zero slowdown or zero interaction with every extension. Promise no intentional mutation of source assets/scenes, explicit resource ownership, compatibility tests and bounded scheduling. A stronger process sandbox is a different architecture.

Sources: [NewPreviewScene](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SceneManagement.EditorSceneManager.NewPreviewScene.html); [RenderTexture](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/RenderTexture.html); [Unity's PreviewRenderUtility source](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Editor/Mono/Inspector/PreviewRenderUtility.cs); [ExecuteAlways](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/ExecuteAlways.html)

## 4. GPU painting and compositing

**Proposed hot path:** rasterize ordered brush dabs into only the affected tile rectangles, with premultiplied-alpha accumulation and explicitly defined flow/opacity semantics. Use hardware blending where its equations match the brush. A 3D brush should project against mesh triangles and a defined brush volume/visibility mask, then rasterize in UV space; a hit UV plus a flat circle alone does not produce a seam-correct surface footprint. Batch submissions without reordering overlapping stamps.

Use compute for dense tile compositing, procedural masks, reductions and filters where measurements support it. One invocation owns each output pixel and evaluates contributing stamps/layers in order, or distinct dispatches impose ordering. Do not parallelize overlapping writes without a valid algorithm; atomics are not a general solution for order-dependent alpha blending. GPU compute is a candidate, not a proven speed win over fragment shaders.

A command buffer records the small dirty workload on the main thread. CPU workers prepare plain-data work lists; they do not submit graphics calls. Use separate source/destination surfaces for read-modify-write blending/filter passes. Hardware blending into a destination without sampling it differs from sampling and writing the same texture. Unity explicitly warns that same-source/destination `Graphics.Blit` is undefined. `Graphics.Blit` draws a full-screen surface, so it is not by itself an efficient dirty-tile/subrectangle brush primitive.

Filters need explicit spatial dependency rules: blur/height-to-normal require halo samples, dirty bounds expand by filter radius, and tile gutters must be refreshed before neighbor filtering or mip generation. Global histogram or flood-fill operations can invalidate a much larger region than a local stroke. Recompute mip levels only for changed outputs where feasible; defer high-cost final-quality work while drawing but produce deterministic final resolution on stroke completion/export. Normal, roughness and height layers require channel-specific blending and precision, not generic color blend equations.

Sources: [Graphics.Blit and ping-pong constraint](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Graphics.Blit.html); [compute shader requirements and platform differences](https://docs.unity3d.com/2022.3/Documentation/Manual/class-ComputeShader.html); [RenderTexture.enableRandomWrite](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/RenderTexture-enableRandomWrite.html)

## 5. Sparse tiles, dirty graph, budgets and memory arithmetic

**Proposed document layout:** sparse logical tiles per layer/channel, with stable tile IDs and revision numbers; a candidate tile size is 256×256, compared against 128 and 512 by benchmark. Keep untouched tiles implicit. Store source tiles and undo records losslessly on disk, with bounded RAM staging and a bounded LRU GPU working set. Use chunked texture-array/atlas pools and a logical page table. This is application-managed sparsity, not a claim of portable hardware sparse-texture allocation. A large preallocated array still consumes its allocated storage.

A dirty-dependency graph links layer/mask/filter/group outputs to affected composite tiles. A cache key includes source revisions, channel/format, blend mode/opacity, mask/filter parameters, color-space policy and relevant neighbor revisions. Change the smallest region, invalidate upward through dependent groups, and reuse unaffected prefix/group results. Cache only intermediates justified by measured reuse. Reordering layers or changing group isolation may invalidate broad portions of the graph. Maintain exact document state independently of disposable previews.

**Calculated lower bounds, not measurements:** for 4096×4096 pixels with no mipmaps, padding or driver overhead: R8 is 16 MiB; R16/R16F is 32 MiB; RGBA8 is 64 MiB; RGBA16F is 128 MiB; RGBA32F is 256 MiB. Full mip chains add approximately one third. One 256×256 RGBA8 tile is 256 KiB. A fully dense stack of 100 RGBA8 color layers alone is 6.25 GiB; naïve double-buffering is 12.5 GiB before masks, normals, undo, preview and Unity/project memory. Thus “many 4K layers” cannot mean keeping two full GPU images for every layer. Sparsity saves space only while content is sparse; filled dense layers require disk-backed paging and compositing throughput.

Color sources may use RGBA8 for an 8-bit document or higher precision when explicitly chosen; use linear higher-precision intermediate accumulation where needed. Masks/scalars use single-channel formats when supported. Preserve signed/float height data when the document requires it. GPU compressed imports are not a suitable directly editable authoritative paint representation. Specify linear versus sRGB interpretation, alpha convention, normal handedness/packing and export quantization explicitly.

**Hardware policy:** 32 GB system RAM / 8 GB VRAM is an indicative common test configuration ONLY. It is not a minimum requirement, admission gate, guarantee, or claimed user machine. 64/16 is an upper comparison tier, not a guarantee either. Include lower-memory/discrete and integrated/shared-memory systems. Scale cache sizes, preview resolution, simultaneous channels, filter refinement and background concurrency to available resources and workload. Never silently reduce saved texture resolution, precision or document content. Lower hardware may process the same document more slowly; unlimited dense-layer interactivity is not promised. Expose memory use, pending refinement and adjustable budgets. Report dense versus sparse load, affected area and simultaneously visible channels alongside layer count.

`SystemInfo.graphicsMemorySize` reports an approximate installed amount, not a reliable free-VRAM budget. Combine conservative defaults, tracked tool allocations, allocation failures and user limits; preserve substantial headroom for Unity/project/OS. Stop admission and shed reconstructible caches before risking data loss. This section's budget design and arithmetic are engineering proposals/calculations, not Unity performance claims.

Source: [SystemInfo.graphicsMemorySize](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SystemInfo-graphicsMemorySize.html)

## 6. Burst and Jobs: use on CPU data, not as a blanket accelerator

**Proposed workloads:** BVH construction/refit and batched triangle queries; UV island adjacency and seam lookup; stroke resampling and footprint/tile binning; curve subdivision/surface tracing; CPU fallback filters and image transforms; lossless block transforms/hashing if the algorithm is Burst-compatible. Copy/acquire immutable mesh data once per source/pose revision and reuse it. Small pointer-sample operations may remain synchronous if scheduling overhead exceeds useful work.

**Verified constraints:** Burst supports a subset of C# and does not generally allow managed objects/reference types. Use unmanaged structures, `NativeArray`/supported containers and `Unity.Mathematics`. Do not pass UnityEngine.Object instances into Burst jobs or call UI, AssetDatabase, renderer/material/texture mutation or GPU submission APIs there. Most Unity API belongs on the main thread; documented self-contained/thread-safe exceptions do exist. Jobs must be scheduled from the main thread; schedule early and complete when output is actually needed. A scheduled job cannot simply be interrupted, and long jobs can monopolize shared workers. Tune batch size and task granularity; avoid one job per dab or immediate `Complete()` after each schedule. Ensure dependencies and ownership before reusing buffers. Dispose all allocations; treat canceled work through generation IDs/cooperative chunk boundaries rather than freeing live memory.

`Mesh.AcquireReadOnlyMeshData` produces snapshots usable from any thread and requires disposal; modifying the Mesh before disposal can force a copy, and the old snapshot does not acquire later changes. Its ordinary API also rejects unreadable input meshes. A separate supported Editor mesh-read adapter can be investigated rather than silently changing import settings. Serialization/encoding/file I/O are separate background tasks, not automatically valid Burst jobs.

Sources: [Burst type support](https://docs.unity3d.com/Packages/com.unity.burst@1.8/manual/csharp-type-support.html); [create/run/schedule/complete jobs](https://docs.unity3d.com/cn/2022.3/Manual/JobSystemCreatingJobs.html); [ParallelFor batching](https://docs.unity3d.com/ja/2022.3/Manual/JobSystemParallelForJobs.html); [thread-safe Unity API exceptions](https://docs.unity3d.com/cn/2022.3/Manual/script-Serialization.html); [Mesh.AcquireReadOnlyMeshData](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Mesh.AcquireReadOnlyMeshData.html)

## 7. Surface paths and deformed meshes

**Proposed representation:** anchors store source mesh identity/topology revision, material/submesh, triangle ID, barycentric coordinates, UV-set identity and an explicit reference-pose/space policy. Barycentric attachment follows the same triangle through skinning without treating screen coordinates as permanent geometry. Surface curves need adjacency-aware tracing or a defined projection algorithm, adaptive subdivision and tangent transport; arbitrary world-space Bézier interpolation can leave the surface or jump to the wrong sheet. Define behavior across UV seams, mirrored/overlapping UVs, thin surfaces, hard-normal borders, disconnected shells and material boundaries. Split UV raster segments at seams. Reject ambiguous reattachment after topology/UV changes or request an explicit rebind; never silently paint another triangle.

Cache an immutable pose snapshot for each editing pose, build/refit picking data from that snapshot and keep preview/picking/strokes on the same revision. Freeze pose during a committed stroke unless live-deformation painting is an explicitly tested feature. `SkinnedMeshRenderer.BakeMesh` creates a snapshot and always runs skinning on CPU even if GPU skinning is enabled, so do not invoke it at every pointer sample. Custom vertex-shader displacement is not established by this API as part of its snapshot: require a deformation adapter, supported replacement pass, or declare that deformation unsupported for exact picking. Avoid claiming all arbitrary shader deformation follows automatically.

`RaycastHit.textureCoord` needs a MeshCollider; `barycentricCoordinate` provides interpolation weights on the hit triangle. These support the anchor concept, not a complete persistent surface-curve system. A tool-owned BVH can avoid repeatedly cooking colliders; performance must be measured.

Sources: [BakeMesh](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SkinnedMeshRenderer.BakeMesh.html); [textureCoord](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/RaycastHit-textureCoord.html); [barycentricCoordinate](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/RaycastHit-barycentricCoordinate.html)

## 8. Undo, save, reload and recovery

**Proposed undo:** a document command history plus before/after deltas or snapshots of touched tiles, captured once per tile per stroke; group one stroke as one operation. Metadata changes can integrate with Unity Undo through a dedicated document/proxy object. Unity's object-state Undo API must not be presumed to capture GPU pixel contents. Maintain lossless tile history explicitly, with bounded in-memory residency and disk spill. Pure replay requires versioned brush algorithms, random seeds, immutable dependencies and checkpoints; GPU floating-point replay across devices is not assumed bit-exact. Preserve exact tile states where fidelity is required.

**Proposed save:** capture an immutable document revision, enqueue GPU copies/readback only for required dirty tiles or final export, retain source resources until requests complete, then encode/write losslessly. Bound concurrent requests and staging bytes. Handle `hasError`, canceled generations and unavailable formats; do not report “saved” until an atomic replacement/manifest commit is durable and verified. Main-thread AssetDatabase import/refresh comes after finished output, not per tile or during strokes. A save can complete a prior revision while new editing continues; the UI must state whether later edits are still dirty.

**Verified:** AsyncGPUReadback provides asynchronous transfer with several frames of latency; this does not make encoding, import or I/O free. Completed request data has a limited lifetime; copy it immediately or use an owned `RequestIntoNativeArray` buffer with a managed lifetime. Do not release temporary RTs before requests complete. Check `SystemInfo.supportsAsyncGPUReadback`, format readback support and errors. Without support, use a deliberate synchronous readback at save/checkpoint boundaries with progress; never place it in the normal pointer loop.

**Encoding caveat:** the English 2022.3 `EncodeNativeArrayToPNG` documentation currently says main-thread-only, while some localized older pages say thread-safe. Do not base an architecture promise on that disagreement. The managed `EncodeArrayToPNG` 2022.3 page explicitly documents thread safety, enabling an owned managed-buffer background encoder after readback; allow and budget its copy/allocation. Alternatively use a separately validated encoder. Neither implies Burst compatibility. Unity PNG output is 8-bit and lacks gamma/profile metadata, so higher-bit-depth/color-managed document export needs an explicit suitable encoder/format contract.

**Recovery:** journal semantic commands/tile records and write periodic durable checkpoints during ordinary editing. GPU contents are a cache, not the sole copy: Unity documents that RenderTexture contents can be lost. On controlled teardown, stop new work, complete relevant jobs, safely drain readbacks before releasing their resources, unregister callbacks, release buffers/RTs/materials and close preview scenes. Recreate on reload from persisted document state. This can cause a bounded visible stall; do not promise synchronous reload is magically async. Handle assembly reload, window disable, play-mode transitions (including domain-reload-disabled configurations), source reimport, graphics-resource loss and ordinary quit. A crash can bypass shutdown callbacks, so only the latest durable checkpoint/journal is guaranteed recoverable. `SessionState` survives assembly reload but is cleared when Unity exits; it is suitable for window/session metadata, not crash-safe painting storage.

Sources: [Undo object-state snapshot](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Undo.RegisterCompleteObjectUndo.html); [AsyncGPUReadback](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Rendering.AsyncGPUReadback.html); [request support/lifetime](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Rendering.AsyncGPUReadback.Request.html); [request result lifetime](https://docs.unity3d.com/cn/2022.3/ScriptReference/Rendering.AsyncGPUReadbackRequest.html); [native-array PNG encoder](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/ImageConversion.EncodeNativeArrayToPNG.html); [managed-array PNG encoder](https://docs.unity3d.com/cn/2022.3/ScriptReference/ImageConversion.EncodeArrayToPNG.html); [assembly reload hook](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/AssemblyReloadEvents-beforeAssemblyReload.html); [play-mode hook](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/EditorApplication-playModeStateChanged.html); [ordinary quit interception](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/EditorApplication-wantsToQuit.html); [SessionState](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SessionState.html)

## 9. Graphics API and feature fallback contract

At session startup inspect actual compute, format sampling/rendering/blending/random-write, texture size/array and readback capabilities; catch allocation/dispatch/readback failures and expose a diagnostic report. `SystemInfo.IsFormatSupported` tests a format for a specified usage; a format being sampleable does not prove it is a writable render target/UAV or readable back. Set `enableRandomWrite` before creating an appropriate compute target.

Proposed levels:
1. Raster paint + compute tile/filter backend + async readback when validated.
2. Raster paint and raster ping-pong compositor/filters if compute or required UAV format is absent; hide only features with no correct fallback.
3. Budgeted CPU fallback for selected supported operations and synchronous save readback when needed, with clear reduced-performance reporting.

Do not globally switch the user's graphics API/pipeline. Explicitly test Windows D3D11/D3D12, macOS Metal and any supported Linux/Vulkan/OpenGL combination that is actually in product scope. Shared-memory devices require a unified pressure budget. Compute shader portability requires initialized resources, valid bounds and all declared resources bound; behavior tolerated by DX11 is not a portability contract. No reliance on texture atomics or undefined source/destination aliasing. Validate color-space conversion, texture orientation, normal packing and output formats on each supported path.

Sources: [SystemInfo.IsFormatSupported](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SystemInfo.IsFormatSupported.html); [compute portability](https://docs.unity3d.com/2022.3/Documentation/Manual/class-ComputeShader.html); [random-write capability](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/RenderTexture-enableRandomWrite.html)

## 10. lilToon adapter: source-verified mapping, version-gated support

The inspected upstream `master` sources are evidence of available properties/semantics on 2026-10-02, not a guarantee for the user's installed version or every Lite/Multi/Gem/transparent variant. Record and test the exact installed release, shader variant, feature settings and render pipeline. `Material.HasProperty` is necessary but not sufficient: a declared property may be inactive because a feature is disabled or compiled out.

Candidate mapping from verified source:
- Base color: `_MainTex`, modulated by `_Color` and other existing material controls
- Normal: `_BumpMap`, `_UseBumpMap`, `_BumpScale`; preserve correct Unity normal encoding, handedness and importer/preview differences
- Metallic: `_MetallicGlossMap` red channel multiplied by `_Metallic`, under reflection feature controls
- Smoothness: separate `_SmoothnessTex` red channel multiplied by `_Smoothness`; do not assume Standard shader metallic-alpha packing
- Roughness: convert explicitly to the shader's smoothness convention; `1-r` is appropriate only when the source convention is matching perceptual roughness, not any arbitrary physical roughness value
- Height: optional `_ParallaxMap` with `_UseParallax`, `_UsePOM`, `_Parallax`, `_ParallaxOffset`; this is shader parallax/POM mapping, not promised mesh displacement or universal height support

Keep an independent authoring channel model and material adapters; never discard unsupported authoring channels. Export them and display an honest unsupported-preview state. Operate on cloned preview materials; apply to source assets only in a requested explicit operation. Feature switches, scalar multipliers, UV transforms and color management are part of mapping validation. Enabling a global lilToon feature/rebuilding its shader settings would exceed mere preview isolation and needs a product decision.

Sources: [upstream lilToon property declarations](https://github.com/lilxyzw/lilToon/blob/master/Assets/lilToon/Shader/lts.shader); [upstream reflection sampling and parallax calls](https://raw.githubusercontent.com/lilxyzw/lilToon/master/Assets/lilToon/Shader/Includes/lil_common_frag.hlsl); [upstream feature settings](https://github.com/lilxyzw/lilToon/blob/master/Assets/lilToon/Editor/lilToonSetting.cs); [Material.HasProperty](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Material.HasProperty.html)

## 11. Validation plan: acceptance hypotheses, not claimed results

Build a small architecture prototype before setting hard performance promises. Record exact Editor/package/OS/API/GPU/driver/tablet/display and project load. Test cold and warm shader/Burst/cache states separately. Measure incremental cost compared with the same project with the window closed.

- Workloads: 1K/2K/4K; 1/16/64/128 layers as selected benchmark points rather than supported maxima; sparse and fully filled layers; small and full-canvas strokes; large blur radii; 1 versus multiple channels; seams/overlap; masked groups; layer reorder/opacity; undo/redo; PSD/export/import at defined sizes
- Geometry: small and high-triangle meshes; static, bones and blend shapes; pose changes; multiple material slots; malformed or changed topology; independent and overlapping UV shells
- Metrics: input-to-visible-stroke latency p50/p95/p99, main-thread and GPU time, maximum stalls, allocation/GC, tracked RAM/VRAM, cache hit/miss/eviction, readback bytes/in-flight count, save latency, recovery completeness and canceled-operation behavior
- Compare raster and compute by affected pixel count, layer depth, brush radius and stamp count; compare 128/256/512 tile sizes; compare synchronous small CPU work against job batches
- Lower-spec configurations must be included. An illustrative 16 GB RAM / 4 GB VRAM machine and an integrated/shared-memory machine may be useful below the 32/8 common tier, but these are test choices, not newly invented minimum requirements. Include 64/16 as an upper tier
- Correctness: golden-image tolerances for alpha/blend/color space and map packing; exact source-layer/undo save round trip; preview/material export consistency; tiles versus dense reference output; no visible tile edges at mips/filter halos
- Reliability: repeated window open/close, resize and focus changes; compilation/reload mid-work; domain reload disabled; quit with dirty data; readback errors; full disk; interrupted writes; low memory; lost RT contents; large undo; source reimport; simultaneously open Scene/Game views and other common extensions

A useful provisional target is responsive input and cancellation while refinement runs, with bounded main-thread/GPU work and no data loss. Any numeric latency/FPS target must name the measured workload and tier; it cannot be asserted as achieved until implemented and tested.
